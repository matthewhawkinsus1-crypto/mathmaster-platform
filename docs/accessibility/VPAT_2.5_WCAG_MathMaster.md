> **DRAFT for the product owner. This is not a published ACR.**
>
> **No assistive technology has been used to test this product.** No one has run NVDA, JAWS, VoiceOver or ChromeVox
> against it. Every claim below rests on three kinds of evidence:
>
> - automated checks (axe-core, a contrast review, keyboard sweeps);
> - the **Chromium accessibility tree** as read by Playwright and CDP (names, roles, descriptions, live regions);
> - source review.
>
> Chromium's accessibility tree is what a screen reader is *given*. It is not what a screen reader *says*. Verbosity,
> browse-mode reading order, how `aria-describedby` is announced, MathLive's math fields, and the behaviour of other
> browsers are all untested.

## Terms

- **Supports**: the functionality has at least one method that meets the criterion without known defects, or meets it with equivalent facilitation.
- **Partially Supports**: some functionality does not meet the criterion.
- **Does Not Support**: the majority of functionality does not meet the criterion.
- **Not Applicable**: the criterion is not relevant to the product.
- **Not Evaluated**: the product has not been evaluated against the criterion (all AAA criteria, and any WCAG 2.2 row that says so).

**How to read the evidence.** Each row cites the test, driver or file behind its claim, all inside this repository:

- `tests/platform/*.test.mjs` and `tests/tools/*.test.mjs` run in CI on every change.
- `tests/browser/*.mjs` are Playwright drivers. The workflow that runs each one is named in [Evaluation methods](#evaluation-methods).

"Found in source" means the defect was read in code on this branch. It has not been measured in a browser. "Supports (source review)" is the same kind of claim for a criterion with no defect to find: the code was read and nothing needing a fix was seen, and nothing was run. "Not evaluated" means nobody has looked.

## Universal design notes (beyond conformance)

- **Vocabulary and Read Aloud** are offered to *every* student in warm-ups, classwork and practice, not only students whose plan lists them. Quizzes, tests and DOLs keep plan-based supports only, and translation stays profile-based. Its built-in language packs are Spanish only (AX08, kept for now): a student with another home language gets authored translations only, and adding one needs a curated pack, a reviewed provider, or an approved machine-translation service, which is a privacy and cost decision. These universal tools are never recorded as delivered plan supports. Vocabulary's terms come from the question and from hints and feedback the student has *seen*: a hint that is still closed adds nothing, so the term list cannot give away what the hint would (AX43, `src/platform/language/seenHelpText.js`, `tests/platform/vocabularySeenHelp.test.mjs`). The glossary has no entry yet for "reciprocal" or "perpendicular", which needs reviewed Spanish before it is added.
- **Assessment safety.** No spoken label, description or announcement says more than the screen shows:
  - Graph descriptions name only what can be read off the grid, and only the kinds of marks while a question can be answered, except for a student whose plan gives them the Graph read-out.
  - Number-line descriptions never give notation.
  - The 3D model's description never classifies the system or names a point the model does not mark.
  - Announcements read the rendered prompt.
- **Work View** keeps the question's "Information you need" card in its own drawer; on a phone it is inside the Task drawer. It stays there on every activity, assessments included (TOOL-12, `tests/browser/workViewReference.mjs`).

## What a human screen-reader pass must cover

None of this has been heard through a screen reader. A tester with NVDA + Chrome (Windows), JAWS + Chrome, VoiceOver + Safari (iPad) and ChromeVox (Chromebook) should go through each of the following on a practice item and on a DOL or test item:

1. **Answering a question with a math field.** MathLive's field: typing, hearing the expression back, the keypad toolbar (arrow keys, key names), and the focus return after a key.
2. **Math in prompts and feedback.** Is each expression read once, in words, in browse mode and in focus mode?
3. **Every figure in Q-8:** the number line (placing and toggling endpoints), the 3D model (rotation; the description in browse mode), the static question graph, the legacy graph workspace and the Graph Story sketch (drawing a line by keyboard too, AX14). Confirm that `aria-describedby` text is actually announced, and when; nothing should leak on the assessment item.
4. **Coordinate planes:** plotting and moving points by keyboard, the plot announcements, and the data table after the question closes.
5. **Tools with radio-style choices** (Matrix Lab, Representation Match, Relation Mapping, MultiAnswerGrader, My Math Path's choice cards): each is one radio group with one Tab stop and arrow keys now. Does a screen reader announce "radio button, 2 of 4" and the chosen state, and does an arrow key both move and choose as the reader's own radio-group keys do?
6. **Dialogs and Work View:** entering and leaving, Escape, the Task / Reference / Help / Language tools drawers, and focus return.
7. **Status messages:** a Check outcome, a plot, a calculator result, a new question, a save failure. Is each heard once, and not twice?
8. **A secure exam end to end**, including the submit confirmation and a proctor pause.
9. **Reviewing a closed question**, including its graph and a typed answer. Its work is read-only now, not `inert` (see 1.1.1): confirm it is read in browse mode, that its group name is announced once, and that nothing in it can be changed.
10. **Live Challenge:** joining, answering a round, and the countdown.
11. **Spanish Translate and Read aloud**, and what a screen reader does with the math inside Spanish text (it is spoken in Spanish now, AX06; confirm the reader switches voice, or at least reads it intelligibly).
12. **Live Challenge's lock (AX21).** After pressing Lock In on a question the player cannot change, the focus note should be heard once ("Answer locked in · checking it…"), not twice; confirm on a choice question and on a typed one, and that the waits for GO and for a resume are still spoken.
13. **Opening a question, speech order (AX28).** On a laptop a new question puts focus in the answer box, and a polite live region says "Question 3 of 8, Practice. Solve …". With each reader, on a practice item and on a DOL item: which does the student hear first, the answer box's name or the question? Is the question heard at all, or cancelled by the focus change? Does it make a difference when the student moves with Next, with Enter, or by choosing the question from the list? What is read when an assignment first opens, where nothing is announced? Only then decide what to change. Three options to try in the same pass, none built: pointing the first answer box's `aria-describedby` at the prompt, so the box is read with its question and nothing depends on timing; making the announcement assertive (it would interrupt the box's own name); or holding focus until the announcement ends (a delayed focus loses early keystrokes).

Record what each reader actually says. Wherever a row above would change, change it.
