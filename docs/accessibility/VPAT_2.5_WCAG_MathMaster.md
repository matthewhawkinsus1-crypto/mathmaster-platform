> **DRAFT for the product owner. This is not a published ACR.**
>
> **No assistive technology has been used to test this product.** No one has run NVDA, JAWS, VoiceOver or ChromeVox
> against it. Every claim below rests on three kinds of evidence:
>
> - automated checks (axe-core, a contrast review, keyboard sweeps);
> - the **Chromium accessibility tree** as read by Playwright and CDP (names, roles, descriptions, live regions);

## Terms

- **Supports**: the functionality has at least one method that meets the criterion without known defects, or meets it with equivalent facilitation.
- **Partially Supports**: some functionality does not meet the criterion.
- **Does Not Support**: the majority of functionality does not meet the criterion.
- **Not Applicable**: the criterion is not relevant to the product.
- **Not Evaluated**: the product has not been evaluated against the criterion (AAA only).

**How to read the evidence.** Each row cites the test, driver or file behind its claim, all inside this repository:

- `tests/platform/*.test.mjs` and `tests/tools/*.test.mjs` run in CI on every change.
- `tests/browser/*.mjs` are Playwright drivers. The workflow that runs each one is named in [Evaluation methods](#evaluation-methods).

"Found in source" means the defect was read in code on this branch. It has not been measured in a browser.

## Universal design notes (beyond conformance)

- **Vocabulary and Read Aloud** are offered to *every* student in warm-ups, classwork and practice, not only students whose plan lists them. Quizzes, tests and DOLs keep plan-based supports only, and translation stays profile-based. Its built-in language packs are Spanish only (AX08, kept for now): a student with another home language gets authored translations only, and adding one needs a curated pack, a reviewed provider, or an approved machine-translation service, which is a privacy and cost decision. These universal tools are never recorded as delivered plan supports.
- **Assessment safety.** No spoken label, description or announcement says more than the screen shows:
  - Graph descriptions name only what can be read off the grid, and only the kinds of marks while a question can be answered, except for a student whose plan gives them the Graph read-out.
  - Number-line descriptions never give notation.
  - The 3D model's description never classifies the system or names a point the model does not mark.
  - Announcements read the rendered prompt.
- **Work View** keeps the question's "Information you need" card in its own drawer; on a phone it is inside the Task drawer. It stays there on every activity, assessments included (TOOL-12, `tests/browser/workViewReference.mjs`).

## What a human screen-reader pass must cover

None of this has been heard through a screen reader. A tester with NVDA + Chrome (Windows), JAWS + Chrome, VoiceOver + Safari (iPad) and ChromeVox (Chromebook) should go through each of the following on a practice item and on a DOL or test item:

1. **Answering a question with a math field.** MathLive's field: typing, hearing the expression back, the keypad toolbar (arrow keys, key names), and the focus return after a key.
2. **Math in prompts and feedback.** Is each expression read once, in words, in browse mode and in focus mode?
3. **Every figure in Q-8:** the number line (placing and toggling endpoints), the 3D model (rotation; the description in browse mode), the static question graph, the legacy graph workspace and the Graph Story sketch (drawing a line by keyboard too, AX14).
